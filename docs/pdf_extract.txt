Re:Learn
Multimodal AI Models, Datasets, and System Implementation Plan
Purpose: Explain which models to build, what each model does, what data is needed, and how the remaining parts
of the system will work. The plan is written for a practical student project, not a system trained from scratch.
1. What we are building
Re:Learn is an adaptive learning system. It should look beyond whether an answer is right or wrong and use the
evidence available in a student's response to identify possible misconceptions, provide a focused explanation, and
check understanding again.
Multimodal meaning: The system can accept more than one kind of input, such as typed text, a selected MCQ
option, a photo of handwritten working, or a diagram. Different input types need suitable processing before the
diagnosis model can use them. The core diagnosis model does not have to be one giant model that directly
understands every format.

2. Model 1 — Multimodal Misconception Diagnosis
Purpose: Identify and differentiate possible misconceptions from the student's answer and any available reasoning,
calculation steps, code, or image.
Model type and recommended base
Item
Recommendation
Model type
Supervised classification using a pretrained language model, with an image-to-text/vision processing path
for visual responses.
Text base model
DeBERTa-v3-base for text classification. DistilBERT is a lighter alternative.
Image path
Use OCR/handwriting recognition to read written work. For diagrams or graphs, use a vision-language
model or a task-specific image parser where needed.
How they work together
Extract text and structured visual details first. Send the question, extracted answer, working, and relevant
context to the diagnosis classifier. Keep the original image for review when extraction is uncertain.
Why this design?
A single text classifier is not automatically able to read photos, handwriting, graphs, and diagrams. A modular design
is easier to build and test: one path handles typed answers, another extracts information from images, and the
diagnosis stage uses the combined evidence. This also lets the team replace an OCR or vision tool without rebuilding
the whole system.
Flow
Student question + response → identify input type → extract text/numbers/diagram details if needed → combine
with question and concept → diagnosis classifier → ranked possible misconceptions + confidence → accept, ask a
follow-up, or mark uncertain.

4. Model 2 — Sequence-Based Misconception Detection
Purpose: Analyze a series of answers in order and find a pattern that may not be visible from one answer alone. This
is your added feature, not a requirement to train a separate model in the problem statement.
Model type and recommended approach
Item
Recommendation
Model type
Sequence classification: a model reads ordered response features and predicts a sequence-level
pattern or misconception.
First implementation
Start with transparent rules and the predictions from Model 1. This gives you a baseline and is easier to
explain.
Model to experiment with
A small GRU (Gated Recurrent Unit), trained on response sequences. A GRU is an architecture, not a
pretrained base model.
Why GRU
It is relatively small and suitable for short quiz sequences. It can learn order and repeated patterns
without needing a large transformer.
Flow
Ordered quiz responses → Model 1 predictions and response features → sequence model/rules inspect related
concepts and changes over time → recurring or connected pattern + confidence → diagnosis service combines this
with individual evidence.

6. End-to-End Prototype Flow
This is the flow the website can demonstrate.
1. Choose a Physics chapter → 2. Attempt quiz questions (MCQ, theory, numerical, and selected image-based
responses) → 3. Process the response (text directly; image through OCR/vision) → 4. Run individual diagnosis
→ 5. Analyze answer sequence if enough responses exist → 6. Combine evidence and confidence → 7. Show a
targeted explanation → 8. Ask a fresh reassessment question → 9. Update the learner profile.
What the demonstration should prove
•
Two students can give the same wrong answer but show different reasoning; the system can produce different
likely diagnoses when the evidence supports it.
•
A photo of a worked solution can be processed and used as evidence, demonstrating the multimodal path.
•
Several related answers can reveal a recurring pattern that a single answer may not show.
•
The intervention is linked to the diagnosis rather than being a generic explanation.
•
A new question checks whether the student's understanding changed, and the learner record updates.
Evaluation targets
Set targets only after measuring a baseline. For an early prototype, you may use the following as goals, not claimed
results:
Metric
Initial target or reporting plan
Individual diagnosis
Aim for 80% accuracy and macro F1 of 0.75 on a properly held-out, representative set; report
per-class results too.
Sequence analysis
Compare against a simple rule-based baseline. Keep the GRU only if it improves held-out results.
Multimodal extraction
Report extraction success and diagnosis performance separately for typed text, handwriting, and
diagrams.
Latency
Measure actual end-to-end time on your demo hardware; do not assume a fixed response time.
Intervention quality
Have a subject reviewer check factual correctness, relevance to the misconception, and clarity.
Reassessment
Report how often students answer the new question correctly, but do not treat one correct answer
as proof of lasting learning.

Re:Learn — End-to-End Component Flow
How the components connect, in simple words, including which model is used at each step.
1. Student answers a quiz
The LMS collects the student's MCQ, written answer, numerical working, or uploaded image.
Used here: LMS and quiz logic — no AI model.
2. Input processing
For images, extract handwriting/text and interpret useful visual information such as diagrams or graphs. Prepare the
result as text and structured features.
Used here: PaddleOCR for text extraction; a suitable vision-language model for visual understanding, if needed.
3. Individual misconception detection
Check one answer and its reasoning to predict possible misconception labels.
Used here: DeBERTa-v3-base text classifier. The backend sends it prepared text (for example, in a JSON API request) and
receives predictions such as labels and confidence scores.
4. Sequence-based misconception detection
Look across the student's answers in question order to find repeated or connected misconception patterns.
Used here: Start with rule-based analysis; optionally train a GRU sequence model. This is Model 2.
5. Combine the diagnoses
Combine the individual prediction with the sequence-pattern result. If evidence is weak or unclear, ask a follow-up
instead of making a confident diagnosis.
Used here: Backend/application logic and confidence thresholds — no separate model required.
6. Generate a personalized explanation
Use the likely misconception and approved learning material to create a targeted explanation.
Used here: Qwen2.5-7B-Instruct with RAG (retrieval from textbook and reviewed content).
7. Reassessment
Give a new question to check whether the student understood the concept.
Used here: Question bank and LMS logic — no AI model required initially.
8. Track learning progress
Save answers, predictions, explanations, and reassessment results so future learning can use that history.
Used here: Database and learner-tracking logic.
In one line: Student input → image/text processing → DeBERTa individual diagnosis → GRU or rules for sequence patterns →
combine evidence → Qwen LLM explanation → reassessment → update learner profile.
Remember: DeBERTa asks, “What misconception might explain this answer?” The sequence model asks, “What pattern across
answers suggests a recurring or connected misconception?” The vision component interprets images; it does not replace the
misconception classifier. This is a proposed design, not a requirement to use these exact models.

Model A: Misconception Detection and Differentiation
Model A does more than mark an answer right or wrong. It predicts which misconception, if any, best explains an
individual student's response.
Two parts of Model A's job
Detection
Identify whether the response suggests a misconception, a correct understanding, a
calculation slip, a unit conversion error, or insufficient evidence.
Differentiation
Distinguish between different misconception classes that may lead to similar incorrect
answers, using the question, student response, and any available reasoning or visual
evidence.
Example
For a question about the relationship between current and resistance, a student might say that increasing
resistance increases current. Model A can predict a relevant misconception label. If another student gives a wrong
numerical result despite using the correct formula, Model A may instead predict a calculation slip. The exact
diagnosis depends on the evidence and the quality of the training examples.
What Model A receives and returns
Input: The question and student's response/reasoning, plus text or structured information extracted from an image
when available. The backend can send this to the deployed classifier through a JSON API request.
Output: One or more predicted labels with confidence scores. The application can use an uncertainty threshold to
avoid forcing a diagnosis when evidence is weak.
How Model B differs
Model A diagnoses one response at a time. Model B analyzes the ordered series of a student's responses to
identify repeated or connected patterns across questions. Model B does not replace Model A; it uses response
history to add sequence-level evidence.
Dataset link: Your individual-response dataset has 900 records and 15 target classes. These classes support
differentiation across misconception types as well as correct, calculation-slip, unit-conversion, and
insufficient-evidence outcomes. This does not guarantee perfect differentiation; performance must be measured on
held-out test data.
